# Feature Specification: Upgrade framework in `scaffold up`

**Feature Branch**: `feature/029-upgrade-framework`

**Created**: 2026-11-20

**Status**: Draft

**Input**: Extend `scaffold up` with a reusable **upgrade-actions** framework so legacy projects (scaffold-ca-python ≤ 0.5.0, no `scaffold_version` in `[tool.scaffold-ca-python]`) can migrate to the wireup layout from spec 028, and future migrations can be added without new CLI commands.

**Related**: [Spec 028 — Wireup DI for new projects](../028-wireup-di/spec.md). Wireup projects are **1.0.0+**. Legacy projects lack the `scaffold_version` key (≤ 0.5.0).

**Supersedes (in part)**: Informal draft in `docs/spec-029-migrate-di/` and the obsolete `scaffold migrate-di` command concept.

---

## Clarifications

### Session 2026-11-20

- **Composition root auto-replace threshold**: Replace `application/app.py`, `main.py`, or other composition-root files only when their on-disk SHA-256 digest matches the digest of the file as rendered by scaffold-ca-python **0.5.0** for the same project metadata; otherwise report `composition_root_modified` as a pending item.
- **Dry-run diff format**: Show a unified diff (standard `---` / `+++` hunks) for every planned overwrite, insert, and append; list-only dry-run for paths alone is not sufficient for migration review.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Legacy 0.5.0 project migrates via `scaffold up` (Priority: P1)

A developer with a project generated by scaffold-ca-python 0.5.0 runs `scaffold up --dry-run` to preview automated transformations and pending manual work, then `scaffold up` to apply them. The command automates pyproject updates, container-to-factory conversion, adapter/helper decoration, and entry-point `Provide` → `Injected` rewrites; it reports every remaining manual change with file, line, and guide section. Post-migration quality checks (`ruff`, `mypy`, `pytest`) are **not** run by the CLI—the developer or an agent uses the migration skill checklist.

**Why this priority**: Without a supported upgrade path, published spec-028 wireup projects cannot coexist with real 0.5.0 codebases in production.

**Independent Test**: Run `scaffold up` against a committed 0.5.0 fixture; verify golden output, `--dry-run` writes nothing, and `--report json` lists automated and pending items. After resolving pending items using the skill, the project test suite passes.

**Acceptance Scenarios**:

1. **Given** a legacy project with a clean git tree, **When** `scaffold up --dry-run` runs, **Then** a unified diff and a list of automated changes plus pending items are shown; no file is written.
2. **Given** a legacy project, **When** `scaffold up` runs (not dry-run), **Then** pyproject is updated, containers become factory files under `application/config/usecases/`, adapters/helpers receive injectable decoration, entry points use `Injected[...]` where applicable, and `wiring.py` / usecase package init are written.
3. **Given** uncommitted changes and at least one applicable upgrade action (non-dry-run), **When** `scaffold up` runs without `--allow-dirty`, **Then** the command exits non-zero with a message to commit or stash first.
4. **Given** a routine `scaffold up` on an already-migrated wireup project with no applicable actions, **When** the command completes, **Then** dependency lock/sync still run and exit zero without redundant file churn.
5. **Given** a project whose declared `scaffold_version` is greater than the installed scaffolder version, **When** `scaffold up` runs, **Then** the user is warned, upgrade actions are skipped, and dependency update steps still behave as today (or are skipped in dry-run per flags).

---

### User Story 2 — Extensible upgrade-action framework (Priority: P2)

A maintainer adds a new upgrade action module to a ordered registry. Each action declares a human-readable name and description, implements content-based detection (`applies`) and migration (`up`), and is idempotent. Order is defined by the registry list; chronology is reflected in module names and enforced by a test.

**Why this priority**: One-off migration commands do not scale as the scaffolder evolves.

**Independent Test**: A no-op action that detects a marker string can be registered; running `scaffold up` twice leaves the tree unchanged after the first run.

**Acceptance Scenarios**:

1. **Given** a project that does not match an action's content predicate, **When** `scaffold up` runs, **Then** that action is skipped with no side effects.
2. **Given** an action that already ran (content markers absent), **When** `scaffold up` runs again, **Then** the action reports no applied items and makes no writes.
3. **Given** two registered actions, **When** `scaffold up` runs, **Then** actions execute in registry order, then `uv lock --upgrade` and `uv sync` run.

---

### User Story 3 — Agent-guided migration with installed skill (Priority: P2)

A developer runs `scaffold install-skill migrate-di [--target all] [--force]` to copy the migration skill into the target project, then asks an AI agent to finish pending items. The agent follows stop conditions in the skill (approval before mutating commands and before any git commit).

**Why this priority**: Automated migration cannot reach 100%; guided completion is required for provider patterns and edited composition roots.

**Independent Test**: With the skill installed, an agent resolves pending items using `references/recipes.md` on the 0.5.0 fixture and runs the skill checklist verification steps (not `scaffold up`).

**Acceptance Scenarios**:

1. **Given** the skill is installed, **When** the agent reads `SKILL.md`, **Then** it verifies preconditions (clean tree when applying writes, green tests baseline) before applying changes.
2. **Given** a pending item with a recipe, **When** the agent applies the recipe, **Then** the affected test passes without unrelated edits.
3. **Given** a pending item with no recipe, **When** the agent encounters it, **Then** it stops and asks the developer.
4. **Given** a project with the skill already installed, **When** `install-skill` runs without `--force`, **Then** it exits without overwriting and prints a hint.

---

### Edge Cases

- `providers.Resource`, `Configuration`, `Selector`, or nested containers → reported as typed pending items with guide anchors and optional skeletons; not silently skipped.
- Composition root or `main.py` edited after generation → `composition_root_modified` pending item unless SHA-256 matches the 0.5.0 render.
- Dry-run chains multiple actions: later actions do not see in-memory effects of earlier actions on disk (documented limitation; users run a real `up` to refresh).
- Legacy guard on `generate-*` commands continues to refuse legacy projects; **only** `scaffold up` (and read-only commands) accept legacy trees for modification via upgrades.

## Requirements *(mandatory)*

### Functional Requirements

#### `scaffold up` and upgrade orchestration

- **FR-001**: `scaffold up` MUST run registered upgrade actions when not disabled, then `uv lock --upgrade`, then `uv sync` (in that order). A `--skip-upgrades` flag MUST skip only the action phase while preserving dependency steps.
- **FR-002**: `scaffold up --dry-run` MUST print unified diffs for all planned file changes and MUST NOT write any file. It MAY list paths that would be created or deleted.
- **FR-003**: `scaffold up` MUST require a clean git working tree only when at least one upgrade action applies and the run is not dry-run, unless `--allow-dirty` is set.
- **FR-004**: Upgrade actions MUST be selected by **content** (e.g. presence of `dependency-injector` imports or dependency declarations), not by filtering solely on `scaffold_version`, so a second run still reports unresolved pending items where needed.
- **FR-005**: The first wireup migration action MUST apply these transforms when applicable: pyproject dependency and tooling keys; container modules to `application/config/usecases/<name>_usecase.py` factories; `@injectable` on adapters/helpers; `Provide` / `Depends(Provide[...])` to `Injected[...]`; create `wiring.py` and usecase package init; remove obsolete container modules; write `scaffold_version` to mark wireup adoption when the action applies changes.
- **FR-006**: Composition root and bootstrap files MUST be replaced automatically only on SHA-256 match against the 0.5.0 render; otherwise they MUST appear as pending items.
- **FR-007**: `scaffold up --report json` MUST print a single JSON document on **stdout**; human-oriented and tool logs (including `uv` and Rich) MUST go to **stderr**.
- **FR-008**: Any failure (precondition, action error, `uv` failure) MUST exit with code **1**. Pending manual items MUST appear in the report and MUST NOT by themselves change the exit code when automated steps succeed.
- **FR-009**: `scaffold up` MUST NOT run `ruff`, `mypy`, or `pytest` after upgrades; verification is defined in the migration skill checklist.
- **FR-010**: When the installed scaffolder version is lower than `scaffold_version` in the target project, the command MUST warn and MUST NOT run upgrade actions.

#### Migration skill and documentation

- **FR-011**: The migration skill MUST ship in the wheel at `scaffold_ca_python/skills/migrate-di/` with `SKILL.md`, `references/recipes.md`, `references/errors.md`, and `references/checklist.md` covering verification steps absent from `up`.
- **FR-012**: `scaffold install-skill migrate-di [--target claude|cursor|agents|all] [--force]` MUST copy the skill to the selected harness directories and append a reference line to `AGENTS.md` (creating it if missing). Without `--force`, an existing installation MUST NOT be overwritten.
- **FR-013**: Pending-item `kind` values in JSON output MUST align with recipe keys in `references/recipes.md` and section anchors in `docs/migration/dependency-injector-to-wireup.md`; a test MUST verify alignment.
- **FR-014**: Root `README.md` MUST document `scaffold up` as the migration entry point and `install-skill migrate-di` once implemented.

#### Cross-spec governance (028)

- **FR-015**: Spec 028 FR-020 and `contracts/generated-files.md` MUST exempt `scaffold up` from the legacy refusal alongside `ca` and `vs`, with a note that migration via `up` is specified here (029). Legacy `generate-*` commands MUST point users to `scaffold up` instead of `migrate-di`.

### Key Entities

- **Upgrade report**: Aggregated result with `automated` and `pending` arrays (see [contracts/upgrade-actions.md](contracts/upgrade-actions.md) and pending-item schema).
- **Pending item**: `{kind, file, line, guide_section, suggested_skeleton?}` — manual follow-up for patterns that cannot be codemodded safely.
- **Applied item**: `{kind, file, description?}` — an automatic change applied or that would be applied in dry-run.

---

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: On the committed 0.5.0 test fixture, `scaffold up` automatically applies at least **70%** of required migration edits (by line count or file count agreed in the implementation plan); the remainder appear as pending items with file and line.
- **SC-002**: `scaffold up --dry-run` on any legacy project never mutates the working tree (verified by checksum or git status).
- **SC-003**: Every `kind` emitted in `--report json` pending output has a matching recipe and migration-guide section.

---

## Assumptions

- Spec 028 is released (wireup for new projects at 1.0.0+).
- Only 0.5.0-style legacy projects are in scope; older scaffolder outputs are unsupported.
- `libcst` may be added as a scaffolder dependency for the DI codemod; import is deferred inside the action to keep CLI startup lean when unused.
- Agent skill targets Claude Code, Cursor, and Agent Skills (`.agents/skills/`).
- A static 0.5.0 fixture is generated once with `uvx scaffold-ca-python==0.5.0` and committed for regression tests.

---

## Out of Scope

- Changing wireup templates for **new** projects (028).
- Projects older than 0.5.0.
- A separate `scaffold migrate-di` command.
- Running quality gates inside `scaffold up`.
- Showing cumulative dry-run diffs across chained in-memory actions (limitation documented in plan).
