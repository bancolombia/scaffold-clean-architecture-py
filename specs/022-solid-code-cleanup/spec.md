# Feature Specification: SOLID refactor and comment cleanup of the scaffolder

**Feature Branch**: `feature/022-solid-code-cleanup`

**Created**: 2026-10-22

**Status**: Draft

**Input**: User description: "Internal refactor of the scaffolder code (all of src/scaffold_ca_python/, excluding the Jinja templates) to apply SOLID, separate responsibilities and make comments precise. The observable behavior of the CLI does not change, except for the project-context loader fix."

## User Scenarios & Testing *(mandatory)*

There are two actors:

- the scaffolder **maintainer**, who reads, modifies and extends the code;
- the **CLI user**, who generates projects and modules.

This feature improves the maintainer experience. The CLI user should notice no change, except for the explicitly allowed changes C-1, C-2 and C-3 (see [contracts/cli-behavior.md](contracts/cli-behavior.md)).

### User Story 1 - CLI behavior intact after the refactor (Priority: P1)

As a CLI user, I keep running the same commands, aliases and flags, and I get exactly the same files, output and `--dry-run` preview as before the refactor.

**Why this priority**: A refactor that changes behavior is a regression. This is the safety net the other stories rely on.

**Independent Test**:
- Run the existing test suite. Only the internal-detail tests listed in research R-08 and the assertions tied to C-1, C-2 and C-3 may change, and that includes the `--dry-run` parity and checksum tests.
- Generate a reference project before and after the change and compare the file trees.

**Acceptance Scenarios**:

1. **Given** a project generated with the previous version, **When** any command (ca, gm, guc, gda, gep, gh, gpipe, vs, dm, up) runs with the same arguments, **Then** the produced files are byte-for-byte identical.
2. **Given** any command with `--dry-run`, **When** it runs, **Then** the preview lists the same files and nothing is written to disk.
3. **Given** invalid input, **When** the command runs, **Then** the same error message and the same exit code are shown, and its resolution hint when it has one. Invalid input here means an invalid name, a project not found, an existing module or incompatible flags.

---

### User Story 2 - Add a new type without touching the commands (Priority: P1)

As a maintainer, I want to add a new entry-point or driven-adapter type by only creating its factory and registering it. The type declares its subdirectory, conflict guards, supported flags and result message, with no change to the command code.

**Why this priority**: This is the main benefit of applying open/closed. Today every new type requires editing several conditional chains spread across the command.

**Independent Test**: A test registers a fake entry-point factory and runs `gep` with that type. It generates its files, applies its guards and shows its message, and no module in `commands/` was modified.

**Acceptance Scenarios**:

1. **Given** a newly registered factory, **When** `gep --type <new>` runs, **Then** the command uses the subdirectory, guards and message declared by the factory.
2. **Given** a factory that does not support a flag (for example `--swagger`), **When** that flag is passed, **Then** the command rejects it with a message that names the type and the flag.
3. **Given** a factory that needs to register a script in the pyproject, **When** the module is persisted, **Then** the registration uses an explicit, typed operation and no magic parameter names.

---

### User Story 3 - Unified and correct project context (Priority: P2)

As a CLI user, I want every command to identify the project the same way, so that `gep` and its option to add MCP tools use the same name as every other command.

**Why this priority**: Today there are 8 copies of the context loader. `gep` reads a different pyproject section than the others, which can produce different package names depending on the command.

**Independent Test**: A regression test creates a project whose `[project].name` differs from `[tool.scaffold-ca-python].name`. `gep` and `gm` must resolve the same context.

**Acceptance Scenarios**:

1. **Given** a pyproject with a `[tool.scaffold-ca-python]` section, **When** any command loads the context, **Then** it uses that section's `name`.
2. **Given** a pyproject without that section, **When** the context is loaded, **Then** the project directory name is used.
3. **Given** a project generated by the tool (where both names match), **When** `gep` runs, **Then** the generated imports and package are the same as before the change.

---

### User Story 4 - Readable code with separated responsibilities (Priority: P2)

As a maintainer, I want each function to do one thing: validate, resolve paths, build, persist or present. Operations with many parameters receive a typed options object, and the logic shared by the commands lives in one place.

**Why this priority**: It lowers the cost of change and review. Today there are functions of more than 200 lines with 11 or 12 positional arguments, and blocks repeated in every command.

**Independent Test**: The linter's complexity check passes with a limit of 10 across the source code. A search confirms there is a single definition of the root locator, the context loader, the `--dry-run` option and the preview-tree builder.

**Acceptance Scenarios**:

1. **Given** the source code, **When** the linter runs with the complexity rules enabled, **Then** no function exceeds a cyclomatic complexity of 10.
2. **Given** the generation commands, **When** we inspect how they locate the project, validate the name, build and show the preview, **Then** they all use the same shared utilities.
3. **Given** the project and pipeline commands, **When** they are tested, **Then** the renderer and the writer can be replaced in tests (they are injected) instead of being module-level global instances.

---

### User Story 5 - Precise, noise-free comments (Priority: P3)

As a maintainer, I want short docstrings in a single style that explain what the code does and why. I don't want comments that repeat the code, decorative banners, or references to Spec Kit task or requirement IDs.

**Why this priority**: It improves readability but does not affect functionality. It can be done after the structural stories.

**Independent Test**:
- A search for ID patterns (T0xx, FR-0xx, US-x, R-xx, Phase N) in the source code returns nothing.
- A review finds no docstrings that list dependency versions or files.

**Acceptance Scenarios**:

1. **Given** the source code, **When** we search for Spec Kit ID references, **Then** there are zero matches.
2. **Given** any docstring, **When** it is reviewed, **Then** it follows a single style (Google), describes purpose and reason, and does not repeat types already in the signature.
3. **Given** an inline comment, **When** it is reviewed, **Then** it explains a non-obvious decision. If it doesn't, it is removed.

---

### User Story 6 - Minor cleanup, output fixes and quality guardrails (Priority: P3)

As a maintainer, I want to:

- remove dead code, unnecessary `noqa`, `assert` used for control flow, and messages that mention nonexistent flags;
- have the CLI output show TOML section names literally;
- have the linter prevent this debt from coming back.

**Why this priority**: These are small fixes, and the guardrail prevents future regressions.

**Independent Test**:
- The linter passes with the new rules enabled (bugbear, simplify and complexity).
- The `gpipe` conflict message no longer mentions `--force`.
- `gep --type restapi --dry-run` shows `[project.scripts]`.

**Acceptance Scenarios**:

1. **Given** a pipeline that already exists, **When** `gpipe` runs, **Then** the error message gives a valid resolution hint (for example, delete or rename the existing file) and does not mention a flag that doesn't exist.
2. **Given** the linter configuration, **When** it runs in CI, **Then** it includes rules B, SIM and C90 with `max-complexity = 10` and passes without errors.
3. **Given** a project, **When** `gep --type restapi --dry-run` runs, **Then** the output literally shows `[project.scripts]`.

---

### Edge Cases

- **pyproject without the `[tool.scaffold-ca-python]` section:** the directory name is used, as the commands other than `gep` already do today.
- **Project name with hyphens** (for example `my-project`): the value used as the Python package name stays in snake_case, as in `gep` today. `python_package` is used if it exists; otherwise the name converted to snake_case.
- **Factory without declared guards or flags:** `subdir` is mandatory. `conflicts` and `supported_flags` default to empty (no extra guards; only flags that every registered type accepts).
- **Unregistered type:** the same error as today is shown, with the list of valid types.
- **Write failure midway through persistence:** the current rollback is kept. The message identifies the file that failed without having to parse the exception text.
- **A new linter rule clashes with a pattern required by a framework:** that rule is explicitly ignored in the configuration, with the reason. The plan verified that no new rule currently requires this.

## Requirements *(mandatory)*

### Functional Requirements

**Behavior preservation**

- **FR-001**: All commands, aliases, flags, exit codes and generated files MUST stay identical, except for what FR-010, FR-016 and FR-021 change.
- **FR-002**: Each command's `--dry-run` preview MUST list the same files and MUST NOT write to disk.
- **FR-003**: Error messages MUST keep their content and resolution hint. The only exceptions are FR-016 and FR-021.
- **FR-004**: Existing Jinja templates MUST NOT be modified. **Adding** new templates is allowed as long as the generated output is byte-for-byte identical.

**Single responsibility**

- **FR-005**: The generation operations and the add-tool-to-entry-point operation MUST be split into steps with one responsibility each:
  - input validation;
  - path and context resolution;
  - building;
  - persistence;
  - presentation.
- **FR-006**: Command operations that receive more than 5 CLI options MUST receive them in a single typed, immutable options object instead of a list of positional arguments.

**Open/closed**

- **FR-007**: Each entry-point, driven-adapter and pipeline factory MUST declare everything specific to its type:
  - the target subdirectory;
  - the conflict guards;
  - the compatible flags;
  - the result message.

  Commands MUST NOT contain conditionals on the concrete type.
- **FR-008**: Adding a new type MUST only require creating its factory and registering it in the corresponding registry.
- **FR-009**: Script registration in the pyproject MUST use an explicit, typed operation of the module builder instead of generic parameters with agreed-upon names.

**Project context**

- **FR-010**: There MUST be a single project-context loader, and every command MUST use it. It reads `name` from `[tool.scaffold-ca-python]` and falls back to the directory name.
- **FR-011**: The Python package name derived from the context MUST stay in snake_case, so that the code generated by `gep` does not change for projects created with the tool.

**Duplication removal**

- **FR-012**: Each of these operations MUST be defined once and reused across all commands:
  - locating the project root, with its error message;
  - validating the name and checking whether the module already exists;
  - building the preview tree;
  - the build→persist sequence;
  - the `--dry-run` option definition.
- **FR-013**: Single-entry registries and the duplicated `_tmpl()` helpers MUST be removed.
- **FR-014**: The project and pipeline commands MUST receive their renderer and writer by injection, with a default value, instead of using module-level global instances.

**Comments and cleanup**

- **FR-015**: The source code MUST NOT contain:
  - references to task, requirement, story or decision IDs (T0xx, FR-0xx, US-x, R-xx, Phase N);
  - decorative banners;
  - comments that repeat the next line.

  Docstrings MUST follow the Google style, be short, and not list dependency versions or generated files.
- **FR-016**: The `gpipe` conflict message MUST give a valid resolution hint and MUST NOT mention flags that don't exist.
- **FR-021**: TOML section names that appear in the output (for example `[project.scripts]`) MUST be shown literally, without Rich interpreting them as markup. This is covered by a test written before the change.
- **FR-017**: The following MUST be removed:
  - dead code;
  - unnecessary `noqa` comments;
  - `assert` used for control flow;
  - `from None` that suppresses no exception.

  Optional parameters MUST be annotated consistently as `X | None`.

**Guardrails**

- **FR-018**: The linter configuration MUST enable the bugbear (B), simplify (SIM) and complexity (C90) rules with a limit of 10. Exceptions MUST be justified in the configuration.
- **FR-019**: The linter, the formatter, the strict type checker and the test suite with ≥80% coverage MUST pass in CI.
- **FR-020**: The FR-010 fix MUST be covered by a regression test written before the change (test-first).

### Key Entities

- **Command options**: immutable values that group an operation's parameters (type, name, swagger, integration flags, dry-run).
- **Module type descriptor**: what each factory declares about itself (subdirectory, guards, supported flags, result message).
- **Project context**: project name, Python package name and root, resolved once from the pyproject.
- **Script registration operation**: a typed entry that the module builder applies to the pyproject on persist.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of the existing tests pass.
  - The only tests that change are the internal-detail tests listed in research R-08 and those tied to the allowed changes C-1, C-2 and C-3.
  - The `--dry-run` parity and checksum tests are not modified.
- **SC-002**: No function in the source code exceeds a cyclomatic complexity of 10. Today 6 functions exceed 10 (the highest is 26).
- **SC-003**: There are zero Spec Kit ID references in the source code. Today 43 lines match the FR-015 pattern.
- **SC-004**: The context loader goes from 8 definitions to 1, and the root locator with its error message goes from 9 to 1.
- **SC-005**: Adding a new entry-point type modifies 0 files in `commands/`. Only the factory is created and one line is added to the registry.
- **SC-006**: No function in `commands/` declares more than 5 parameters (positional or keyword) without grouping them in an options object, in line with FR-006.
- **SC-007**: Coverage stays at 80% or higher, and the linter with the new rules passes without errors.

## Assumptions

- **Scope:** all of `src/scaffold_ca_python/` (commands, core, factory, models). Existing templates and the generated code are out of scope. The only additions to the templates directory are the two new templates allowed by FR-004.
- **Compatibility with existing projects:** in projects generated by the tool, `[project].name` and `[tool.scaffold-ca-python].name` match, so the fix does not change their output. It only changes for hand-edited projects where the two names differ.
- **Rule B008:** it does not fire, because Typer is used with `Annotated` (measured in the plan). No ignore is needed.
- **Constitution v2.1.0:** it applies. Two pre-existing violations are kept under the "Pre-existing violations" governance clause:
  - VI: missing resolution hints;
  - II: template contexts passed as `dict`.

  Both are documented in the plan's Complexity Tracking, with follow-up features 023 and 024. This feature introduces no new code that violates a principle.
- **Tests:** tests may be reorganized or renamed when the internal symbols they import change, but their assertions on observable behavior do not change, except for C-1, C-2 and C-3.
- **Delivery:** the refactor can be delivered in several commits per story, as long as each commit leaves the suite green.
