# migrate-di

`scaffold up` automates most of the migration and reports the rest as **pending items** (`kind`, `file`, `line`, `guide_section`). You finish those items with `references/recipes.md`, then verify with `references/checklist.md`. `scaffold up` never runs ruff, mypy or pytest and never commits.

## Stop conditions

- Ask the user before running `scaffold up` without `--dry-run`, and before any `git commit`.
- If the git tree is dirty, ask the user to commit or stash; do not pass `--allow-dirty` on your own.
- If a pending `kind` has no section in `references/recipes.md`, stop and ask the user.
- If the legacy test suite fails before migrating, report it and ask whether to continue.

## Which path

- Project generated by scaffold-ca-python 0.5.0 → follow **Flow** below.
- Project created before the scaffolder (no `[tool.scaffold-ca-python]` in `pyproject.toml`, or the scaffolder says so) → read `references/pre-scaffold.md` first (adoption, then the same flow), and expect configuration/resource decisions that need the user.

## Flow

1. Baseline: run the project's tests on the legacy tree and note the result.
2. Preview: `scaffold up --dry-run --report json` → read `automated` and `pending`; show the user the diff (stderr).
3. Apply (after approval): `scaffold up --report json`.
4. For each pending item, apply the recipe for its `kind`. Keep edits limited to the reported file and what the recipe names.
5. Re-run `scaffold up --dry-run --report json` until `pending` is empty and the action is skipped.
6. Run every step of `references/checklist.md`; fix failures using `references/errors.md`.
7. Summarize the changes and ask the user before committing.
